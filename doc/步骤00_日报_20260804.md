# 2026-08-17

任务 1：深入理解ARP加以太网帧封装结构

一：为什么需要ARP

在以太网（局域网）中，主机之间需要真正的通信，最终必须通过mac地址在数据链路层hh传输帧。

但是上层应用（比如i浏览器、ping）使用的是ip地址。

ip地址是逻辑地址，可以随意规划；mac地址是网卡出厂时烧录的物理地址。

所以需要一种机制，将ip地址→ MAC 地址 进行解析

二：ARP 保证网络通畅的基本原理

arp的工作分为请求和应答两过程：

1.**请求方广播 ARP Request**

目的 MAC = `FF:FF:FF:FF:FF:FF`（广播）

询问：“谁的 IP 是 `169.254.1.1`？请告诉我你的 MAC 地址”

**2.目标主机单播 ARP Reply**

目的 MAC = 请求方 MAC（单播）

回复：“我是 `169.254.1.1`，我的 MAC 是 `00:00:01:02:04:05`”

**3.请求方收到 Reply 后，建立 IP↔MAC 映射** ，之后就可以直接构造以太网帧通信，不再需要广播

**本项目中的实现：**
FPGA 作为被查询的主机，收到 ARP Request 后：

检查目的 MAC 是否为广播或本机 MAC

检查目标 IP 是否等于本机 IP

检查操作码是否为请求（0x0001）

构造 ARP Reply，发送回请求方

代码流程 `arp_reply()`：

**text**

```
读取目的 MAC → 校验
读取目标 IP → 校验
读取操作码 → 校验
构造 42 字节 ARP Reply → 补零到 64 字节 → 推送发送
```

三.ARP 表如何操作？

通用概念：
ARP 表（ARP 缓存）是一张记录 IP地址 ↔ MAC地址 的表，存储在主机内存中。
操作系统会自动维护它，常见操作包括：

添加：收到 ARP Reply 或免费 ARP 时，更新表项。

查询：发送 IP 包前，先查表，有则直接用 MAC；没有则发 ARP Request。

老化：每个表项有生存时间（TTL），超时后删除，重新解析。

删除：收到冲突的 ARP 信息或手动清除。

本项目中的情况：
FPGA 作为 被动响应方，只回复 ARP 请求，不主动发起 ARP 请求，因此 没有维护 ARP 缓存表。
PC 端（如 Windows/Linux）会自动维护 ARP 缓存，记录 FPGA 的 IP↔MAC 映射。

所以在本项目中，ARP 表的操作完全由 PC 完成，FPGA 只管应答，简化了设计。

四、以太网帧结构 + ARP/ICMP 封装图示

1. 以太网帧通用格式
   text
   +----------------+----------------+----------+---------------------+--------+
   |   目的MAC (6)  |   源MAC (6)    | 类型 (2) |      数据 (46~1500) | FCS(4) |
   +----------------+----------------+----------+---------------------+--------+
   目的 MAC：接收方物理地址

源 MAC：发送方物理地址

类型：标识上层协议，如 0x0800=IP，0x0806=ARP

数据：上层协议的数据单元

FCS：帧校验序列，用于 CRC 错误检测

2. ARP 报文封装在以太网帧中
   ARP 直接封装在以太网帧中，类型字段为 0x0806。

text
+----------------+----------------+--------+--------------------------------+--------+
| 目的MAC (6)    | 源MAC (6)      | 0x0806 |       ARP 报文 (28字节)        | FCS(4) |
+----------------+----------------+--------+--------------------------------+--------+
ARP 报文内部结构（28 字节）：

text
+-----------+-----------+----------+----------+----------+
| 硬件类型  | 协议类型  | 硬件长度 | 协议长度 | 操作码   |
| (2)       | (2)       | (1)      | (1)      | (2)      |
+-----------+-----------+----------+----------+----------+
| 发送方MAC | 发送方IP  | 目标MAC  | 目标IP   |
| (6)       | (4)       | (6)      | (4)      |
+-----------+-----------+----------+----------+
本项目中：

硬件类型 = 0x0001（以太网）

协议类型 = 0x0800（IPv4）

硬件长度 = 6（MAC 地址 6 字节）

协议长度 = 4（IP 地址 4 字节）

操作码 = 0x0001（请求）或 0x0002（应答）

发送方/目标 MAC 和 IP 按大端序排列

3. ICMP 报文封装在 IP 包中，再封装在以太网帧中
   ICMP（Ping）不是直接封装在以太网帧，而是先封装在 IP 数据报里，IP 再封装在以太网帧中。

text
+----------------+----------------+--------+---------------------------------------------+--------+
| 目的MAC (6)    | 源MAC (6)      | 0x0800 | IP头(20) | ICMP头(8) | ICMP数据(可变) | FCS(4) |
+----------------+----------------+--------+----------+-----------+----------------+--------+
以太类型 = 0x0800（IP）

IP 头中 协议号 = 1 标识上层是 ICMP

ICMP 头：

类型（1 字节）：0x08=Echo Request，0x00=Echo Reply

代码（1 字节）：固定为 0

校验和（2 字节）

标识符（2 字节）

序列号（2 字节）

ICMP Echo 请求/应答的数据部分通常包含时间戳和填充数据，用于计算往返时延和满足最小帧长。


## 任务 2: 理解 IP 协议 + 验证 ARP + JTAG 外灌固件调试 + 了解 RGMII/GMII

### 一、IP 协议（IPv4）

**1. IP 头结构（固定 20 字节，不含选项）**

| 字段 | 帧内偏移 | IP头内偏移 | 字节 | 说明 |
| --- | --- | --- | --- | --- |
| ver/IHL | 14 | 0 | 1 | 高4位版本=4，低4位头长(单位4字节)=5 |
| TOS | 15 | 1 | 1 | 服务类型，一般 0 |
| 总长度 | 16~17 | 2~3 | 2 | IP头+数据总字节数 |
| 标识 | 18~19 | 4~5 | 2 | 分片重组用 |
| 标志+片偏移 | 20~21 | 6~7 | 2 | 分片相关 |
| TTL | 22 | 8 | 1 | 生存时间，每跳减 1 |
| 协议号 | 23 | 9 | 1 | 1=ICMP、6=TCP、17=UDP |
| 头校验和 | 24~25 | 10~11 | 2 | 只校验 IP 头 20 字节 |
| 源 IP | 26~29 | 12~15 | 4 | 发送方 |
| 目的 IP | 30~33 | 16~19 | 4 | 接收方 |

> 帧内偏移 = 14（以太头）+ IP头内偏移，`OFF_IP_*` 宏就是这些值。

**2. 封装关系**

IP 封装在以太网帧里（以太类型 `0x0800`），IP 之上再封装 ICMP/TCP/UDP。ping 的完整封装是：以太帧 → IP 头 → ICMP 头，三层套娃。

**3. 本项目 ip_proc() 的校验流程（c/ip.c）**

收到 IP 包后做四步：

1. 校验 ver/IHL：版本必须 4，头长 >= 5（最小 20 字节）
2. 校验目的 IP == 本机 IP（`Local_IP_ADDR`）
3. 缓存源 IP（供应答时交换地址）
4. 读协议号分发：1=ICMP、6=TCP、17=UDP，其他丢弃

**4. IP 头校验和**

只覆盖 20 字节 IP 头，**不含数据**。应答时 `ip_header_update()` 干三件事：交换源/目的 IP、更新总长度、重算校验和；TTL/TOS/标识等不变字段从 RX 原样拷到 TX。

### 二、验证 ARP

1. **ping 触发 ARP**：PC 执行 `ping 169.254.1.1`，若 ARP 缓存没有此 IP，先广播 ARP 请求，收到 FPGA 应答建立映射后才发 ICMP Echo
2. **抓包**：`sudo tcpdump -i eno1 -n arp`，看 ARP Request（目的 MAC 广播）→ ARP Reply（单播）两条
3. **看缓存**：`ip neigh show` 或 `arp -a`，查到 169.254.1.1 对应的 FPGA MAC
4. **清缓存重测**：`sudo ip neigh flush all` 后 ping，重新看到完整请求→应答

### 三、RGMII/GMII 接口

| | GMII | RGMII |
| --- | --- | --- |
| 数据线 | 8bit 收发 | 4bit 收发（DDR 双沿） |
| 时钟 | 125MHz（千兆） | 125MHz（双沿等效 250M） |
| 引脚数 | 24 根 | 12 根（减半） |
| 用途 | 芯片间/板内 MAC-PHY | 板级 MAC-PHY（引脚少） |

一句话：RGMII 是 GMII 的**引脚减半版**，用 4bit + DDR（上下沿各传 4bit）达到和 GMII 8bit 一样的速率。本板 PHY RTL8211F 用 RGMII 接 FPGA。

### 四、JTAG 外灌固件调试

**背景**：以前固件用 updatemem 编译期合进 bit，改一行 C 要重综合十几分钟。现在改成「纯硬件 bit 只烧一次 + JTAG 灌固件」。

**踩了 3 个坑**：

1. 烧录后 `get_hw_axis` 返回空 → HW Manager 缓存旧 JTAG 链，必须 `refresh_hw_device`
2. `create_hw_axi_txn` 缺 name 参数 → 事务创建失败
3. **写固件 ~50 秒期间 CPU 不读 RX FIFO，被 PHY 广播包写满破坏网络 → ping 不通**（最隐蔽）

**解决**：

1. 所有 JTAG 脚本补 `refresh_hw_device`
2. 事务写 `create_hw_axi_txn <name> $hw_axi -type ...`
3. 改 RTL：`cpu_channel` 复位 `sys_rst_n` → `sys_rst_n & riscv_reset_l[0]`，写固件期间网络 FIFO 保持清空

## 任务 1: 从头理解 — arp 层 (c/arp.c)

今天学习了 ARP 协议，用自己的话总结：

### 一、ARP 的三重校验

1. **目的 MAC** 是本机 MAC 或广播
2. **目标 IP** 等于本机 IP
3. **操作码**为 ARP Request

三道全过才放行，任一不过直接丢弃。

### 二、ARP 应答帧哪些字段需要修改

- 目的 MAC → 请求方 MAC
- 源 MAC → 本机 MAC
- 操作码 → Reply（0x0002）
- 发送方 MAC/IP → 设为本机
- 目标 MAC/IP → 设为请求方
- 以太类型、硬件/协议类型等 → **保持不变**

### 三、填充到 64 字节是为什么

以太网帧有**最小长度限制**（64 字节，不含 CRC），小于该值的帧会被接收方丢弃，所以必须补零填充。

### 四、ARP 请求的广播 MAC 是什么？代码中如何识别？

1. 广播 MAC 是 `FF:FF:FF:FF:FF:FF`
2. 代码通过 `dst_mac_high == 0xFFFFFFFFu && dst_mac_low == 0xFFFFu` 来识别

### 五、为什么 eth_proc() 已识别 ARP 类型，arp_reply() 还要再校验 MAC？

因为 ARP 请求可能是广播，`eth_proc()` 只处理 IP 单播，所以 ARP 的 MAC 校验必须在 `arp_reply()` 内部完成，**不能复用** IP 的 MAC 校验逻辑。

### 六、ARP 帧结构（42 字节 + 补零到 64）

| 偏移  | 字段       | 值                    |
| ----- | ---------- | --------------------- |
| 0~5   | 目的 MAC   | ← 请求方 MAC         |
| 6~11  | 源 MAC     | ← 本机 MAC           |
| 12~13 | 以太类型   | ← 0x0806 (ARP)       |
| 14~15 | 硬件类型   | ← 0x0001             |
| 16~17 | 协议类型   | ← 0x0800 (IPv4)      |
| 18    | HLEN       | ← 6 (MAC 地址长度)   |
| 19    | PLEN       | ← 4 (IP 地址长度)    |
| 20~21 | 操作码     | ← 0x0002 (ARP Reply) |
| 22~27 | 发送方 MAC | ← 本机 MAC           |
| 28~31 | 发送方 IP  | ← 本机 IP            |
| 32~37 | 目标 MAC   | ← 请求方 MAC         |
| 38~41 | 目标 IP    | ← 请求方 IP          |
| 42~64 | 补零       |                       |

### 七、ARP 缓存是什么？FPGA 需要维护吗？

1. ARP 缓存是主机存储 **IP↔MAC 映射的表**，避免每次通信都发 ARP 请求
2. FPGA 设计是**被动响应** ARP 请求、不主动发起，因此**不需要维护 ARP 缓存**——只有 PC 需要缓存 FPGA 的 MAC 地址

### 八、如果收到 ARP 响应，代码怎么处理？

`arp_reply()` 校验操作码时，如果 `arp_type != ARP_REQUEST` 就直接返回、不处理响应。因为本设计只做 ARP 应答方，不主动请求。

### 九、ARP 是什么？

- **A** = Address（地址，指 IP 地址）
- **R** = Resolution（解析 / 转换）
- **P** = Protocol（协议）
- ARP = **地址解析协议**，本质是 **IP 地址 → MAC 地址** 的翻译协议

### 学到了什么

**arp 层（arp.c/arp.h）**：干两件事——① 三道"安检"把关：先看帧的目的 MAC 是不是本机或广播、再看问的目标 IP 是不是 `169.254.1.1`、最后看操作码是不是 ARP Request，三道全过才放行；② 构造应答：把请求帧里"发送方"换成本机 MAC/IP，把请求方地址抄回"目标"字段，做出 42 字节的 ARP 应答，补零到 64 字节最小帧长，推给 MAC 发出去。

**关键的一句话**：ARP 请求→应答就是"镜像翻转"——请求里"谁问的"(sender)，应答里变成"答给谁"(target)。

### 关键精髓

- **纯服务端、零缓存**：FPGA 只应答、从不主动查 ARP，所以根本没有 ARP 缓存表，整个 `arp.c` 就一个 `arp_reply()` 函数。这就是"被 ping"场景下的极致精简。
- **eth 查过的 MAC，ARP 为什么再查一遍**：`eth_proc()` 对 ARP 包是直接放行（因为 ARP 请求是广播帧，eth 层的单播过滤器会误杀它），所以 MAC 检查下沉到 `arp_reply()` 自己做，且放行"本机单播 OR 广播"两种目的 MAC。
- **不动字段从 RX 原样抄**：硬件类型/协议类型/HLEN/PLEN/以太类型这些请求和应答一模一样的字段，直接从 RX 拷到 TX，不硬编码——抄的永远和请求方一致，还省代码。
- **不用结构体、用偏移量**：`arp.h` 里明明定义了完美的 `arp_frame_t` 结构体，但代码一个都没用——因为 RX/TX FIFO 是寄存器寻址的字节流，没有内存地址给你 struct 指针访问。结构体是"说明书"，真正的解析靠 `OFF_ARP_*` 偏移量"按图索骥"。
- **补零到 64 字节**：42 字节的 ARP 帧低于以太网最小帧长 64 字节，会被接收方当坏帧丢弃，所以 TX[42..63] 补 0 凑够最小帧。

## 任务 1: 从头理解 — 寄存器头文件 + eth 层

### 学到了什么

**寄存器头文件（lcpu_general.h）**：把一堆硬件寄存器的地址和读写操作，封装成一个个 C 宏（`LCPU_RD_DATA8()`、`LCPU_WR_BYTE()` 这些）。固件代码里直接调宏就行，不用背那些 `0x80000000` 开头的裸地址——相当于给硬件做了个"遥控器"。

**eth 层（eth.c/eth.h）**：干两件事——① 读以太网帧的"类型字段"（字节 12-13），看是 `0x0800`(IP) 还是 `0x0806`(ARP)，决定这个包丢给谁；② 判断是发给本机的包后，**顺手把回包的 MAC 头先写进 TX FIFO**（把对方的 MAC 拷过来当目的 MAC），这样上层 ip/arp 就不用再管 MAC 头了——"边收边发，省一步"。

### 关键精髓

- **偏移量就是协议栈的"地图"**：`OFF_ETH_TYPE=12`、`OFF_IP_SRC_IP=26`…… 每个字段在帧里的位置用宏定义好，解析就是"按图索骥"。
- **分层思想**：eth 只认"以太类型"这一件事，IP/ARP 的事它不管，丢给上层。每层职责单一，改哪层不影响别的层。

## 任务 1: HTTP 协议栈编写 — Web 控制面板

### 目标

在已跑通的 TCP 协议栈之上，实现第三步「HTTP 请求响应」：浏览器访问 `http://169.254.1.1` 打开控制面板，点按钮远程读写 FPGA 寄存器、控制板载 LED。

### 进展和结果

新增 `c/http.c` + `c/inc/http.h`，并把 HTTP 解析逻辑融入 `c/tcp.c` 的 `tcp_handler()`，形成完整的「TCP 承载 HTTP」链路：

```
浏览器 ──TCP 80──► PicoRV32
                    └─ tcp_handler() [ESTABLISHED]
                         ├─ 读 payload 首字节 'G' → GET 处理
                         │    ├─ GET /          → 返回 main_page (控制面板)
                         │    └─ GET /set?addr=…&data=…&mode=… → 寄存器读写
                         ├─ 读 payload 首字节 'P' → POST 处理
                         │    └─ 解析 JSON 或 form-urlencoded → 寄存器读写
                         └─ send_http_data() → MSS 分段 + 末段 FIN → 关闭连接
```

**1. 网页内容与协议栈分离（`c/http.c`）**

网页字符串单独放在 `http.c`，协议栈 `tcp.c` 只做「解析 + 发送」，改页面不动协议栈：

| 常量              | 作用                                                                       |
| ----------------- | -------------------------------------------------------------------------- |
| `main_page`     | 控制面板首页：LED 独立开关 + 全亮/全灭 + 寄存器读写表单                    |
| `post_response` | 操作结果页模板，占位符`XXX` / `0x00000000` / `0x88888888` 运行时填充 |

纯 HTML + 内联 CSS，**不用 JavaScript**（之前跨域 CORS 预检问题折腾很久，纯 HTML 更稳定）；控制动作全部用 `<a href='/set?…'>` 链接或 `<form method=GET>` 实现，浏览器一次点击就是一个独立 HTTP 请求。

**2. HTTP 解析辅助函数（`c/tcp.c` 第 8 部分）**

| 函数                     | 作用                                                                            |
| ------------------------ | ------------------------------------------------------------------------------- |
| `tcp_find_form_field`  | 在 payload 里线性扫描 form-urlencoded 的`key=value`（GET 查询串 / HTML form） |
| `tcp_find_json_field`  | 扫描 JSON 的`"key":"value"`（curl POST）                                      |
| `read_ascii_hex_field` | 8 字符 ASCII 十六进制 → uint32                                                 |
| `to_hex_string`        | uint32 → 8 字符大写十六进制                                                    |
| `build_post_response`  | 用`strstr` 等长替换结果页模板里的占位符                                       |
| `send_http_data`       | 按 MSS 1460 分段发送，末段带 FIN                                                |

**3. GET/POST 分发逻辑（`tcp_handler()` ESTABLISHED 分支）**

ESTABLISHED 收到带数据包后：

- 读 payload 首字节判断方法（`'G'` → GET，`'P'` → POST）
- GET 且 URL 含 `addr=` → 解析 `addr/data/mode` 三字段做寄存器读写
- GET 且无 `addr=` → 返回主页面 `main_page`
- POST → 先试 JSON 解析，失败回退 form-urlencoded（兼容浏览器表单和 curl）
- `mode=read` → `LCPU_REG32_READ()`；`mode=write` → `LCPU_REG32_WRITE()` + 置 `tcp_led_override=1` 暂停流水灯
- 响应发送完立即 `close_connection()`（HTTP 短连接模式）

### 关键设计点

1. **等长占位符替换**：`XXX` 与「读/写」（UTF-8 各 3 字节）、`0x00000000`/`0x88888888` 与 8 字符十六进制长度一致，替换不改变字符串总长，省去重算响应长度和 buffer 再分配的麻烦。
2. **MSS 分段 + FIN 序号**：`send_http_data()` 把响应按 1460 字节切段，每段重算 TCP 校验和、推进 `conn_snd_seq`；末段附加 FIN 并在 FIN 后再 `seq++`（FIN 额外消耗一个序号），否则对端 ACK 号对不上。
3. **双格式 POST 解析**：`tcp_find_json_field` 失败自动回退 `tcp_find_form_field`，同一个服务端同时兼容 `curl -d '{"addr":…}'` 和浏览器 `<form>` 提交。

## 任务 2: HTTP 调试 — x86 原生全链路仿真

### 目标

不依赖 RTL 仿真器（Icarus/Verilator，慢）和 FPGA（要烧录），在 PC 上用 x86 gcc 直接编译固件 C 代码，秒级验证「TCP 三次握手 + HTTP GET/POST」全链路。

### 进展和结果

创建 `sim/mock_lcpu.h`（硬件抽象 mock 层）+ `sim/test_http.c`（测试主程序），把固件所有 RISC-V 硬件依赖替换成 PC 实现：

| 硬件接口                     | x86 Mock                 | 说明                     |
| ---------------------------- | ------------------------ | ------------------------ |
| `LCPU_REG32_WRITE/READ`    | `mock_reg[]` 数组      | 寄存器 → 内存           |
| `LCPU_SET_LED`             | `printf("[LED]=0x%x")` | LED → 终端              |
| `LCPU_LOCAL_TIME_L()`      | 自增软件计数器           | rdcycle → static uint32 |
| `LCPU_RD_DATA8()` 等       | `sim_rx_buf_ptr[]`     | RX FIFO → 内存 buffer   |
| `LCPU_WR_BYTE/PUSH_PACKET` | `sim_tx_buf[]` + 长度  | TX FIFO → 内存 buffer   |

测试分 4 个 Phase，手动构造以太帧（MAC + IP + TCP + Payload）逐 Phase 注入 `eth_proc() → ip_proc() → tcp_handler()` 调用链：

```
Phase 1: [SYN]          → 验证 SYN+ACK 发出, flags=0x12
Phase 2: [ACK]          → SYN_RECEIVED → ESTABLISHED
Phase 3: [PSH+ACK] GET  → 验证响应含 "HTTP/1.1" "200" "RISC-V"
Phase 4: [PSH+ACK] POST → 验证响应 "200" (注: 短连接关闭后需重新握手)
```

编译命令：

```bash
cd sim
gcc -DSIM_FAST -I. -I../c/inc -I../c \
  -o test_http test_http.c ../c/tcp.c ../c/eth.c ../c/ip.c \
  ../c/icmp.c ../c/arp.c ../c/http.c ../c/comlib.c
./test_http
```

结果：**Phase 1~3 共 7 项断言全部 PASS（0 FAIL）**，TCP 三次握手 + HTTP GET 全链路秒级通过；Phase 4 POST 因 Phase 3 短连接已关闭而未通过（预期行为，需重新握手再测）。

### 遇到的问题

1. **`rdcycle` 是 RISC-V 汇编指令**：x86 上编译报 `no such instruction: rdcycle`。解决：mock 层用 `static uint32_t` 软件计数器替代，固件 `LCPU_LOCAL_TIME_L()` 只做相对计时、不需要精确周期。
2. **`LCPU_REG32_WRITE/READ` 指针转换警告**：`LCPU_BASE=0x80000000` 在 64 位系统上超出用户空间地址，报 `cast to pointer from integer of different size`。解决：mock 层 `#undef` 后重定义为数组访问，不依赖真实地址。
3. **IP 头 protocol 字段遗漏（最隐蔽）**：Phase 1 构造 SYN 包时只填了 ver/IHL 和 total_len，`pkt[23]` 默认 0 而非 `0x06(TCP)`，导致 `ip_proc()` 读到 `protocol=0x00` 返回 NO_PROC、TCP 分支根本进不去。debug 时在 mock 的 `LCPU_RD_DATA8` 加 printf 发现 `RD[23]=0x00`，补齐 IP 头 18~25 字节后修复。
4. **Mock 头文件 include 顺序**：固件 `.c` 用 `#include "inc/lcpu_general.h"` 会命中真实头文件、覆盖 mock。解决：gcc `-include inc/lcpu_general.h` 强制预注入 + mock 头抢先定义 `_LCPU_GEN_H_` 阻挡后续 include；同时补 mock `_WR()` 宏（`send_tcp_segment` 有 `_WR(6)=1u` 强制 TX 刷新）。
5. **Phase 4 POST 未过（预期行为）**：Phase 3 的 GET 响应已 `close_connection()`（短连接），连接回到 CLOSED，紧接着的 POST 包被当作新连接处理、不会返回 200。这是 HTTP 短连接模式的固有特性，不是 bug，要测 POST 需在 Phase 3 后重新走一次握手。

### 收获到的经验

1. **协议栈与网页内容分离**：网页字符串单独放 `http.c`，`tcp.c` 只负责解析和发送。改页面（换颜色、加按钮）完全不碰 TCP 状态机，协议栈稳定性不受 UI 改动影响。
2. **x86 mock 层是验证协议栈的最快手段**：通过 `-include` + 抢先定义 include guard 注入 mock，不改固件一行代码就在 PC 上编译，把「烧录→上板→抓包」的分钟级迭代变成秒级。仿真测逻辑、上板测数据，两者互补。
3. **等长占位符替换**：用 `strstr` 等长替换模板占位符，避免因 UTF-8 中文（读/写各 3 字节）或十六进制长度变化导致重算响应长度。
4. **MSS 分段要管好序号**：每段发送都要推进 `conn_snd_seq`，末段 FIN 还要额外 +1，漏掉会导致对端 ACK 号不匹配、连接卡死。
5. **首字节方法判断的局限**：用 payload 首字节 `'G'/'P'` 区分 GET/POST，没有完整解析 HTTP 方法行和版本号，属于资源受限下的精简实现。后续要支持更多方法（HEAD/OPTIONS）或 POST 分片时需补全解析。

## 任务 3: fpga_ila 调试 — 引脚冲突 + 时序收敛 + UART 释放

### 目标

在 RISC-V WebSoC 中集成 fpga_ila 调试系统，通过 UART 把内部信号波形抓回 PC，用于调试 MAC/TCP/HTTP 协议交互。

### 根因排查（三个问题层层剥开）

**问题 1：引脚冲突（ping 不通的直接原因）**

加了 ILA 后 ping 不通。查板级引脚定义 `~/work/FPGA_Prj/ACX75035TXDC/ACX750_CB_PIN.xdc` 发现，之前分配的 ILA UART 引脚 T19/R19 根本不是空闲 GPIO：

| ILA 占用            | 实际板载功能 | 连到哪里                   |
| ------------------- | ------------ | -------------------------- |
| T19（ila_uart_rxd） | QSPI_CS      | QSPI Flash MX25L12845 片选 |
| R19（ila_uart_txd） | LCD_R[2]     | RGB TFT LCD 红色数据位     |

板子型号确认为 **ACX750（ALINX AX7A35T）**，这两个引脚都实打实连在板载器件上，ILA UART 占用它们会造成电气冲突。

**问题 2：时序违例（CPU 卡自检的原因）**

最初 17 探针配置里，把 125MHz 域的 GMII/MAC 信号（`gmii_rxd`/`gmii_txd`/`mac_rx_data` 等）挂到了 50MHz 采样的 ILA 上，形成跨时钟域（CDC）违例：WNS=-1.629ns，81 个违例端点。

**问题 3：lcpu-jtag 模式未验证（走弯路）**

试图把 `lcpu_type` 从 "uart" 改成 "xilinx"（用 jtag_cpu_xilinx 释放 UART），结果 CPU 不跑、ping 不通。查 git 历史发现：项目从开始到现在 `lcpu_type` 一直是 "uart"，xilinx 模式（jtag_axi_0 的 JTAG→AXI 桥）**从来没被上板验证过**，依赖运行期 JTAG host，在"烧录完就拔线"的场景下不可用。

### 修复方案

1. **换引脚**：ILA UART 从 T19/R19 改到板载 UART 的 L21/M21。
2. **探针纯 50M 化**：去掉 125M 域探针，只保留 CPU 总线侧 50M 信号，总宽 70bit，时序收敛（WNS=+1.544ns，零违例）。
3. **释放 UART**：`lcpu_type` 保持 "uart"（验证过的模式），把 LCPU 的 `uart_rx` 接高电平 `1'b1`（UART 空闲态），`uart_lcpu_top` 静默；顶层 `uart_rx/uart_tx`（L21/M21）给 ILA。
4. **固件加载不变**：固件照旧走 `updatemem` 合入 bitstream + JTAG 烧录，不经过 UART 那条加载通道。

### 最终 ILA 探针配置（5 探针，70bit，纯 50M 域）

| 探针   | 信号        | 位宽 | 用途         |
| ------ | ----------- | ---- | ------------ |
| probe0 | bus_address | 32   | CPU 访问地址 |
| probe1 | bus_wdata   | 32   | CPU 写数据   |
| probe2 | bus_req     | 1    | 总线请求     |
| probe3 | bus_ack     | 1    | 总线应答     |
| probe4 | led_val     | 4    | LED 状态     |

### 收获到的经验

1. **板级引脚不能想当然**：T19/R19 看着像"空闲 GPIO"，实际是 QSPI_CS/LCD_R[2]。分配引脚前先查官方板级约束文件，别凭引脚号猜。
2. **ILA 采样时钟要和探针信号域匹配**：50M 采样 125M 信号是欠采样（低于奈奎斯特），加 false_path 也抓不到准确波形。要么 ILA 挂 125M 抓 GMII/MAC，要么挂 50M 抓 CPU 总线。
3. **别贸然切换未验证的模式**：lcpu_type 的 xilinx 分支虽然 RTL 存在，但从来没上板跑过，切过去会踩 jtag_axi_0 的集成坑。判断"代码支持"前先查 git 历史确认真的验证过。
4. **UART 释放的巧妙做法**：固件加载走 updatemem（编译期合入 BRAM），根本不经过 lcpu 的 UART 通道，所以把 `uart_rx` 接高让 uart_lcpu_top 静默即可腾出 UART，不用动加载模式。

## 任务 1: x86 原生单元测试 — TCP/HTTP 全链路仿真 ✅

### 目标

不依赖 RTL 仿真器（Icarus/Verilator）和 FPGA 硬件，在 PC 上直接用 x86 gcc 编译固件 C 代码，秒级验证 TCP 三次握手 + HTTP GET 全链路逻辑。

### 进展和结果

**1. Mock 层设计 (`sim/mock_lcpu.h`)**

创建了 x86 兼容的硬件抽象层，把所有 RISC-V 硬件依赖替换为 PC 端实现：

| 硬件接口                         | x86 Mock                            | 说明                   |
| -------------------------------- | ----------------------------------- | ---------------------- |
| `LCPU_REG32_WRITE(addr, data)` | `mock_reg[addr] = data`           | 寄存器写 → 内存数组   |
| `LCPU_REG32_READ(addr)`        | `mock_reg[addr]`                  | 寄存器读 → 内存数组   |
| `LCPU_SET_LED(v)`              | `printf("[LED]=0x%x\n", v)`       | LED 操作 → 终端打印   |
| `LCPU_LOCAL_TIME_L()`          | `static uint32_t t=0; return t++` | rdcycle → 软件计数器  |
| `LCPU_RD_DATA8()`              | `sim_rx_buf_ptr[sim_rx_addr]`     | RX FIFO → 内存 buffer |
| `LCPU_WR_BYTE(addr, data)`     | `sim_tx_buf[addr] = data`         | TX FIFO → 内存 buffer |
| `LCPU_WR_PUSH_PACKET(len)`     | `sim_tx_pkt_len = len`            | 发包触发 → 记录长度   |

关键技术点：用 `#ifndef _LCPU_GEN_H_` + `#define _LCPU_GEN_H_` 抢先定义 include guard，搭配 gcc 的 `-include inc/lcpu_general.h` 强制注入 mock 头文件，阻止真实的 `lcpu_general.h` 被固件源文件 include。这样不改固件一行代码，就能在 x86 上编译。

**2. 测试流程 (`sim/test_http.c`)**

测试分三个 Phase，模拟完整的 TCP 客户端行为：

```
Phase 1: PC → FPGA   [SYN]  seq=PC_ISN
         FPGA → PC   [SYN+ACK] seq=ISN, ack=PC_ISN+1
         → 验证: sim_tx_pkt_len >= 40, TCP flags = 0x12

Phase 2: PC → FPGA   [ACK]  seq=PC_ISN+1, ack=ISN+1
         → 状态转移: SYN_RECEIVED → ESTABLISHED

Phase 3: PC → FPGA   [PSH+ACK] GET / HTTP/1.1\r\nHost: 169.254.1.1\r\n\r\n
         FPGA → PC   [ACK+FIN] HTTP/1.1 200 OK...
```

### 遇到的问题

1. **`rdcycle` 是 RISC-V 汇编指令**, x86 上编译报错 `no such instruction: rdcycle %eax`。解决：在 mock 层用 `static uint32_t` 软件计数器替代，固件中 `LCPU_LOCAL_TIME_L()` 不需要精确计时。
2. **`LCPU_REG32_WRITE/READ` 宏的指针转换在 x86 上报 warning**（`cast to pointer from integer of different size`），因为 `LCPU_BASE = 0x80000000` 在 64 位系统上超出用户空间地址。解决：在 mock 层 `#undef` 后重新定义为数组访问，不依赖真实地址。
3. **IP 头字段遗漏**: Phase 1 的 SYN 包构造时只填了 `ver/IHL` 和 `total_len` 两个字节，协议字段 `pkt[23]` 默认初始化为 0 而非 0x06(TCP)，导致 `ip_proc()` 读到 `protocol=0x00` 返回 NO_PROC。debug 时在 mock 层 `LCPU_RD_DATA8` 加 printf 发现 `RD[23]=0x00`，补齐 IP 头 18-25 字节后修复。
4. **Mock 头文件的 include 顺序**: 固件的 `.c` 文件通过 `#include "inc/lcpu_general.h"` 引入真实头文件，Mock 层即使放在 `-I.` 路径中也会被 `../c/inc/` 中的真实文件覆盖。解决：gcc 用 `-include inc/lcpu_general.h` 强制预注入，且 mock 头文件抢先定义 `_LCPU_GEN_H_` 阻挡后续 include。同时需要 mock `_WR()` 宏（`send_tcp_segment` 有 `_WR(6) = 1u` 强制 TX 刷新）。

### 任务 1: TCP/IP 三次握手与四次挥手原理总结

**目标:**
重新梳理 TCP 协议核心机制，对照 RFC 793 和 tcpdump 抓包数据，把三次握手和四次挥手的每一步 seq/ack 变化、状态转移理解透彻。

**完成:**

1. **三次握手流程验证:**

   ```
   PC                              FPGA (169.254.1.1:80)
    | --- [SYN] seq=PC_ISN -------> | CLOSED → SYN_RECEIVED
    | <-- [SYN+ACK] seq=ISN,       |
    |     ack=PC_ISN+1 ----------- | 发送 SYN+ACK
    | --- [ACK] seq=PC_ISN+1,      |
    |     ack=ISN+1 --------------> | SYN_RECEIVED → ESTABLISHED
   ```

   关键点: SYN 消耗一个序列号（即使没有数据），所以 ACK 的确认号是 seq+1。
2. **四次挥手流程验证 (被动关闭，FPGA 作为服务端):**

   ```
   PC                              FPGA
    | --- [FIN] seq=X, ack=Y -----> | ESTABLISHED → CLOSE_WAIT
    | <-- [ACK] seq=Y, ack=X+1 --- | 确认对方的 FIN
    | <-- [FIN+ACK] seq=Y,         |
    |     ack=X+1 ----------------- | CLOSE_WAIT → LAST_ACK
    | --- [ACK] seq=X+1,           |
    |     ack=Y+1 -----------------> | LAST_ACK → CLOSED
   ```

   关键点: FIN 也消耗一个序列号，自己的 FIN 和确认对方的 FIN 可以合并为一个 FIN+ACK 包。
3. **TCP 校验和学习:**

   - 校验和覆盖「伪首部(12B) + TCP头 + 数据」，伪首部包含源/目的IP、协议号、TCP长度
   - 序列号是字节流编号，不一定是包编号——如果发了 100 字节数据，下一个 seq 就 +100
   - TIME_WAIT 等 2MSL（约 2 秒）是为了确保对方收到最后的 ACK，防止旧连接包干扰新连接

**学习记录:**

- 状态机一共 8 个状态: CLOSED → SYN_RECEIVED → ESTABLISHED → (FIN_WAIT_1/FIN_WAIT_2/CLOSE_WAIT/LAST_ACK/TIME_WAIT) → CLOSED

> ⚠️ **后续还需要加强**: 三次握手和四次挥手的状态转移目前只是照着 RFC 793 的图走了一遍，遇到同时关闭（两端同时发 FIN）和半关闭（一端关了另一端还在发数据）这些特殊情况还不太熟。TCP 状态机的 8 个状态之间的转移条件需要再花时间逐个吃透，后面写代码时才能少踩坑。

### 任务 2: TCP 服务器端 — 上位机稳定控制板载 LED

**目标:**
基于 TCP 协议栈，用 Python 写上位机脚本通过 TCP 短连接发 LED 命令到 FPGA，实现稳定远程控制。

**完成:**

1. **Python 上位机脚本** (`tcp_led_client.py`，~70 行):

   ```python
   # 使用方式: python3 tcp_led_client.py 0x0F
   import socket
   s = socket.socket()
   s.connect(("169.254.1.1", 80))
   s.send(b'\x05')      # 发 LED 命令字节
   s.recv(1024)          # 收 Echo 回显
   s.close()
   ```

   - `0x0F` → 全亮，`0x00` → 全灭，`0x01` → LED0 亮
   - 每轮完整走完: TCP 连接 → 握手 → 数据 → LED 变化 → 挥手 → 断开
2. **流水灯冲突解决:**

   - 全局标志 `tcp_led_override`，TCP 控灯时置 1，主循环检测到后跳过流水灯更新
3. **多连接支持:**

   - TCP 从单连接重构为 4 连接槽位（并行数组管理），为后面浏览器多连接访问做准备
   - 固件 10.5KB / 20KB (51.2%)

**验证结果:**

```
python3 tcp_led_client.py 0x00 → 全灭 ✓
python3 tcp_led_client.py 0x05 → LED0+LED2 ✓
python3 tcp_led_client.py 0x0F → 全亮 ✓
```

**遇到的问题:**

1. **旧连接 FIN 重传干扰**: 每次 TCP 短连接结束后 PC 端延迟发 FIN，旧 FIN 可能在下一轮连接建立后到达，触发误处理。解决: 在 `tcp_handler` 入口校验 src_port，不属于当前连接的包直接丢弃。
2. **流水灯覆盖 LED 控制值**: TCP 发命令设置 LED 后约 1 秒就被主循环流水灯覆盖。解决: `tcp_led_override` 标志位，TCP 写 LED 时置 1，主循环检测到后跳过流水灯更新。
3. **TX FIFO 发包延迟约 200ms**: `LCPU_WR_PUSH_PACKET` 之后数据不是立即发出，要等下一次 RX 活动才推出去。解决: push 之后加 `_WR(6) = 1u` 强制刷新 TX FIFO。

> ⚠️ **后续还需要加强**: 目前 TCP 服务程序（`tcp.c`）虽然跑通了，但有些细节还没完全消化——比如 `send_http_data` 里 MSS 分段的逻辑、`tcp_periodic_check` 里 SYN 重传和空闲超时的定时器管理。参考代码里的多连接管理（16 连接 vs 现在的 4 连接）也需要对比理解清楚。计划把 `tcp.c` 逐函数注释一遍，加深对整个 TCP 协议栈工作流程的理解。

### 任务 1: TCP 协议栈步骤 5~6 — 数据传输 + 完整四次挥手 + 保洁定时器

**目标:**
在已完成的三次握手（步骤 1~4）基础上，补全 TCP 协议栈的后半部分。

**完成:**

**步骤 5 — 数据传输与确认:**

- ESTABLISHED 状态下解析 TCP 数据长度（`ip_total - ip_hdr_len - 20`）
- 从 RX FIFO 逐字节读取 payload 到栈上 buffer
- 更新 `tcp_rcv_ack = seq_num + data_len`，发送 Echo 回显（`send_echo_packet()`）
- 新增带 payload 的校验和函数 `tcp_checksum_with_payload()` 和带 payload 发送函数 `send_tcp_segment_with_payload()`

**步骤 6 — 四次挥手（7 状态完整状态机）:**

- 主动关闭: Echo 后 `send_fin()` → `FIN_WAIT_1` → 收 ACK → `FIN_WAIT_2` → 收对方 FIN → `TIME_WAIT` → 2s 后回 `CLOSED`
- 被动关闭: ESTABLISHED 收到 FIN → 回 ACK → 发 FIN → `LAST_ACK` → 收 ACK → `CLOSED`
- 同时关闭: FIN_WAIT_1 收到对方 FIN → 回 ACK → 直接 `TIME_WAIT`
- RST 处理: `tcp_handler()` 入口检测 `flags & TCP_FLAG_RST` → 直接 `tcp_init()` 重置
- 新增 `send_fin()`、`send_rst()` 发送函数

**步骤 7 — 保洁与超时（`tcp_periodic_check()`）:**

- SYN+ACK 重传: SYN_RECEIVED 下每 3s（150M ticks）重发，最多 3 次，超时回 CLOSED
- 空闲踢连接: 6s（300M ticks）无活动 → 发 RST → CLOSED
- TIME_WAIT 回收: 主动关闭后 2s（100M ticks）自动释放

**修改/创建的文件:**

- `c/tcp.c`（707 行）、`c/inc/tcp.h`、`c/main.c`

**遇到的问题:**

1. **序列号管理**: SYN 和 FIN 各消耗一个序号，初版 `send_fin()` 忘记 `tcp_snd_seq++`，导致挥手阶段对方 ACK 号对不上，连接卡在 FIN_WAIT_1。TCP 协议规定 SYN/FIN 即使不带数据也占一个序号。
2. **被动关闭状态转移**: 对方发 FIN 时，不仅要回 ACK，自己的 FIN 也要等应用层处理。初版直接跳到 CLOSED 跳过了 LAST_ACK，导致对方收不到我们的 FIN，重传超时。
3. **保洁定时器与主循环协作**: `tcp_periodic_check()` 每轮主循环调用一次，但主循环收包频率远高于保洁间隔（~μs vs ~s）。需要 `tcp_last_activity` 和 `tcp_last_tx_time` 两个独立时间戳分别跟踪活动和重传，否则收包会重置重传计时。
4. **IP 头更新时机**: `send_tcp_segment` 和 `send_syn_ack` 都调用 `ip_header_update()`，该函数从 RX FIFO 读原始 IP 头字段（TTL/TOS/ID）再写回。如果 RX FIFO 为空（发包不是收包响应），IP 头字段读到的是总线超时值 `0xDEAD`，导致 IP 头损坏。TCP 发包必须严格在收包处理流程内调用。

**解决方法/经验总结:**

- SYN/FIN 消耗序号是 TCP 协议硬规定，每次 `send_syn_ack()`/`send_fin()` 后紧跟 `tcp_snd_seq++`
- 被动关闭走完整状态链: ESTABLISHED→(收 FIN)→CLOSE_WAIT→(发 FIN)→LAST_ACK→(收 ACK)→CLOSED
- 保洁用 `tcp_last_activity`（任何收包刷新）和 `tcp_last_tx_time`（仅发包刷新）两个独立时间戳
- TCP 所有发送必须在 `eth_proc()` 已写 MAC 头 + `ip_header_update()` 已写 IP 头之后，TX FIFO 里 MAC+IP+TCP 三层顺序写入

### 任务 1: TCP 三次握手全链路仿真验证

**目标:**
通过 Icarus iverilog 仿真验证 TCP 三次握手全链路（`eth_proc → ip_proc → tcp_handler → send_syn_ack → send_ack`）。

**完成:**

1. **仿真通过**: LED `1111→0000→0001(SYN_RECEIVED)→1111(ESTABLISHED)`，状态机完整走过三次握手
2. **核心技术路线**: SIM_FAST 下将 RX/TX FIFO 宏重定向到内存 buffer，绕过 bus 超时和 iverilog `force` 动态注入的限制
3. **BFM 加载 557 条固件指令**，19ms 仿真时间完成

**遇到的问题:**

**问题 1: iverilog force 不可靠**
尝试用 `force` 在 testbench 中动态注入 TCP SYN/ACK 包到 RX FIFO。Phase 1 读到了 MAC 层数据，但 Phase 2（ACK 注入）直接失败——`force` 的 RHS 只求值一次，iverilog 不支持动态数据更新。这条路走不通。

**问题 2: RX FIFO 读超时拖慢仿真**
`send_syn_ack()` 内部调 `ip_header_update()`，该函数从空 RX FIFO 读 20 字节，每次 bus 超时 0xF000 周期，合计 24ms 仿真时间。在 iverilog 全 SoC 仿真下，这需要数小时才能跑完。

**解决: SIM_FAST 宏重定向**
在 `lcpu_general.h` 的 SIM_FAST 分支下，把所有 RX FIFO 读宏（`LCPU_RD_EMPTY`、`LCPU_RD_DATA8` 等）和 TX FIFO 写宏（`LCPU_WR_BYTE` 等）重定向到内存 buffer。固件侧用 `sim_process_packet()` 把硬编码的 TCP SYN/ACK 包数据拷贝到 buffer，然后走完整调用链。仿真时间从数小时缩短到 2 分钟。

**问题 3: Phase 2 ack_num 匹配**
全调用链版本中 Phase 2 的 ack_num 校验差了一个增量——`ip_header_update()` 在写 TX 时会修改一些共享的 buffer 指针，导致 Phase 2 读包时偏移错位。简化自测（跳过 TX 发送，只测状态机）后 LED 正确走到 0x0F。TX 发送和校验和的正确性由硬件（Wireshark/tcpdump）补充验证。

**遇到的问题:**

1. **编译错误**: `ip.c` 调用 `icmp_process(frame, len)` 只传 2 参，函数定义要 3 参；缺少 `ETH_MAX_FRAME_LEN` / `lcpu_local_time_l` 定义
2. **Ping 不通**: FPGA 以太网完全静默，tcpdump 显示 PC 发了 ARP 请求但 FPGA 无应答

**解决方法/经验总结:**

1. **编译问题**: 补上 `ip_total_len` 提取和 `icmp_len` 计算，`ETH_MAX_FRAME_LEN` 移到 `eth.h`，`lcpu_local_time_l` 用 `rdcycle` 替代软件计数器
2. **Ping 不通（关键踩坑）**: 通过分析和对比发现，LCPU 的 RX FIFO 访问有严格规则:
   - **永远不关 REN**（读使能保持为 1）
   - **每帧 POP 两次**（头部弹出包数据，尾部弹出推进到下一包）
   - **直接从 RX/TX FIFO 读写**，不能拷贝到内存缓冲区再处理
   - 初版代码用缓冲区 + `LCPU_RD_STOP()` 关 REN，导致 FIFO 卡死
3. 最终方案: 采用 FIFO 直接读写模式，重写 `main.c` + 精简 `comlib.c`，复用已验证的 `eth.c`/`arp.c`/`ip.c`/`icmp.c`

### 任务 2: TCP 协议栈第 1 步 — 发送发动机

**目标:**
先写"发送发动机"——不依赖接收逻辑，可独立调试验证。

**完成:**

- 实现了 TCP 发送核心函数:
  - `fill_tcp_header()` — 填充 20 字节 TCP 头（端口/序列号/确认号/标志/窗口，全大端）
  - `tcp_checksum_build()` — 伪首部 + TCP 头 + 载荷 → 校验和（严格按 RFC 793）
  - `send_tcp_segment()` — 写 TCP 段到 TX FIFO → `LCPU_WR_PUSH_PACKET`
- 基于发送原语封装了 `send_syn_ack()` / `send_ack()` / `send_rst()`

**遇到的问题:**

- **独立测试发不出包**: 起初试图在 `main()` 启动时独立发送 SYN+ACK，自己构造完整以太网帧（MAC + IP + TCP），但 Wireshark 抓不到任何包
- 原因分析: `ip_header_update()` 在写 IP 头时会从 RX FIFO 拷贝部分字段（TOS、ID、TTL 等），而独立发送时 RX FIFO 为空，导致写入的是随机值；同时 MAC 头也未正确写入

**解决方法/经验总结:**

- TCP 发送不能脱离收包流程独立运行: MAC 头由 `eth_proc()` 在处理收包时写入，IP 头由 `ip_header_update()` 写入，TCP 层只写 TCP 段
- 步骤 1 的代码逻辑正确，但验证需要等步骤 2（接收解析）打通后才能进行
