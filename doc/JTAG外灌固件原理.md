# JTAG 外灌固件原理

> 一句话：**任何 CPU 都要回答「程序怎么进内存」这个问题。JTAG 灌固件就是其中一种答案——上电后通过 JTAG 通道把固件逐字写进指令 RAM，然后释放复位让软核跑起来。** 这套原理可泛化到 MCU bootloader、调试器 load、OTA 升级等几乎所有嵌入式加载场景。

---

## 一、本质：CPU 怎么「跑起来」

CPU 没有记忆，它只会做一件事：**从 PC 指向的内存地址取一条指令，执行，PC+4，再取下一条**。

```
CPU (riscv32_top)
   │
   │  PC = 0 → 去指令 RAM[0] 取指令
   │  ┌───────────────┐
   │  ▼               │
   └─ 指令 RAM ───────┘
      (16KB = 4096 字)
```

所以「让 CPU 跑起来」= 两个条件：

1. **指令 RAM 里有有效的代码**
2. **复位释放**（PC 清零，从 0 开始取指）

FPGA 软核里**没有操作系统、没有启动过程**——程序不在硬盘里，就在那块双口 BRAM 里：有就是有，没有就是取到 `0x00000000`（非法指令 trap 死循环）。

## 二、程序进内存的三条路（所有 CPU 系统的共同问题）

| 方式 | 什么时候写进内存 | 改代码代价 | 本项目状态 |
|------|----------------|-----------|-----------|
| ① 编译期焊死 | bitstream 生成时，`updatemem` 写进 BRAM 初始值 | 重综合整个 bit（~15 分钟） | 旧方案 |
| ② **运行时外灌** | 上电后，通过加载通道逐字写入 | 几十秒（只需灌固件） | **本次方案** |
| ③ 外部存储启动 | 上电后从 Flash/SD 搬到 RAM | 最快，但需额外硬件 | 未用 |

**JTAG 灌固件 = 方式②**。核心价值：**硬件（bit）和固件（C 代码）彻底解耦**——RTL 不动，改多少 C 都只是「外部输入指令」，不用碰 Vivado。

## 三、为什么「能灌进去」——双口 RAM

这是整个方案的物理前提。指令 RAM 是**双口**的：

```
          ┌──────────────────────────────┐
口1 ◄─────┤                              ├─────► 口2 (program_wr)
(CPU 取指/ │      指令 RAM (BRAM)          │ (外部加载通道)
 读写)     │                              │
          └──────────────────────────────┘
```

- **口1** 给 CPU 取指/读写
- **口2**（`program_wr`）给外部加载器用——通过 LCPU 总线访问地址 `0x10000+i`

所以「外灌固件」的本质 = **通过口2 把指令逐字写进 RAM，然后释放复位**。CPU 用的是口1，两边不冲突。

## 四、数据通路——从 PC 到指令 RAM 的 6 跳

```
┌──────────────────────────────────────────────────────────┐
│ PC 终端 (vivado -mode batch -source jtag_load_fw.tcl)     │
│   create_hw_axi_txn / run_hw_axi  ← 发一个 AXI 事务       │
└──────────────┬───────────────────────────────────────────┘
               ▼
┌──────────────────────────────┐
│ JTAG 扫描链 (BSCANE2 原语)    │  ← 挂 USER1/USER2 用户指令链
│ jtag_axi_0 (JTAG→AXI Master) │  ← Xilinx 官方 IP, 把 JTAG 变成 AXI master
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ axi2lcpu (AXI → LCPU 总线)    │  ← 简单 FSM, 一次一拍, 不支持突发
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ lcpu_merge (双 master 仲裁)   │  ← 加载器优先, CPU 次之
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ lcpu_fpga_test (地址译码)      │  ← 0x100 复位 / 0x10000+i 指令 RAM
└──────────────────────────────┘
```

| 跳 | 模块 | 职责 |
|----|------|------|
| 1 | `create_hw_axi_txn` | Vivado 命令，构造一个 AXI 读/写事务 |
| 2 | `jtag_axi_0` | 官方 IP，把 JTAG 扫描链变成 AXI master（BSCANE2 挂 USER1/USER2） |
| 3 | `axi2lcpu` | AXI 协议 → LCPU 总线，一次一拍，`-len 1` 不支持突发 |
| 4 | `lcpu_merge` | 仲裁加载器 / CPU 两条 master，加载器优先 |
| 5 | `lcpu_fpga_test` | 地址译码：`0x100` 复位寄存器、`0x10000+i` 指令 RAM |

**最关键的一层是 `lcpu_merge`**——两个 master 抢一条总线，必须保证加载时 CPU 不抢。

## 五、为什么写固件前必须先按住复位

`lcpu_merge` 是仲裁器。如果 CPU 在跑，它也在发总线请求（取指、读写外设），会跟加载器抢。

安全顺序：

```
① 写 0x100 = 0   → 按住 CPU 复位（CPU 不发请求，加载器独占总线）
② 逐字写 0x10000+i → 固件灌进指令 RAM
③ 写 0x100 = 1   → 释放复位，CPU 从 PC=0 开始跑
```

> ⚠️ 本项目踩过的坑：复位期间 CPU 不读网络 RX FIFO，被 PHY 广播包写满破坏网络。修复 = 让网络 FIFO 的复位跟随 CPU 复位（`sys_rst_n & riscv_reset_l[0]`），写固件时网络 FIFO 保持清空。

## 六、字节序细节

```
firmware.bin (RISC-V 小端字节流)
  第 i 个 32 位字 = bin[4i..4i+4] 按 <I 小端解出
  → 写到指令 RAM 地址 0x10000 + i  (注意: i 是"字地址", 不是字节地址)
```

验证：`firmware.bin[0..3] = 6f 00 d0 14` 解出 `0x14D0006F`，正是 `reset_entry` 的 `j program_main`。所以释放复位后 CPU 从 PC=0 取到的第一条指令就是跳进主程序——**JTAG 灌固件与 updatemem 完全等价**。

## 七、泛化：这套原理的应用场景

| 场景 | 加载通道 | 关键差异 |
|------|---------|---------|
| **本项目 JTAG 灌固件** | JTAG→AXI 桥 | PC 用 Vivado 当宿主 |
| **MCU bootloader** | UART/I2C/SPI/USB | 固件里先跑一小段引导程序，接收外部数据写 Flash |
| **调试器 load 程序** | JTAG/SWD（gdb load、openocd program） | 通过调试接口写内存 + 复位 |
| **FPGA 软核下载** | Vivado/Quartus 调试工具 | MicroBlaze/Nios II 在调试器里「load app」 |
| **在线升级 OTA/ISP** | 网络/串口 | 产品出厂留 bootloader，运行时收新固件 |
| **仿真 BFM 加载** | lcpu_bfm 读脚本 | 用 `jwrite` 文本在仿真里模拟同一件事 |

**共享思维模型**：

> ① CPU 复位 / 进 bootloader（不让应用代码抢资源）
> ② 外部数据 → 逐字节/逐字写进内存（RAM 或 Flash）
> ③ 释放复位 / 跳转到新程序入口
