一：为什么需要ARP

在以太网（局域网）中，主机之间需要真正的通信，最终必须通过mac地址在数据链路层传输帧。

但是上层应用（比如浏览器、ping）使用的是ip地址。

ip地址是逻辑地址，可以随意规划；mac地址是网卡出厂时烧录的物理地址。

所以需要一种机制，将ip地址→ MAC 地址 进行解析

二：ARP 保证网络通畅的基本原理

arp的工作分为请求和应答两过程：

1.**请求方广播 ARP Request**

目的 MAC = `FF:FF:FF:FF:FF:FF`（广播）

询问：“谁的 IP 是 `169.254.1.1`？请告诉我你的 MAC 地址”

**2.目标主机单播 ARP Reply**

目的 MAC = 请求方 MAC（单播）

回复：“我是 `169.254.1.1`，我的 MAC 是 `00:00:01:02:04:05`”

**3.请求方收到 Reply 后，建立 IP↔MAC 映射** ，之后就可以直接构造以太网帧通信，不再需要广播

**本项目中的实现：**
FPGA 作为被查询的主机，收到 ARP Request 后：

检查目的 MAC 是否为广播或本机 MAC

检查目标 IP 是否等于本机 IP

检查操作码是否为请求（0x0001）

构造 ARP Reply，发送回请求方

代码流程 `arp_reply()`：

**text**

```
读取目的 MAC → 校验
读取目标 IP → 校验
读取操作码 → 校验
构造 42 字节 ARP Reply → 补零到 64 字节 → 推送发送
```

三.ARP 表如何操作？

通用概念：
ARP 表（ARP 缓存）是一张记录 IP地址 ↔ MAC地址 的表，存储在主机内存中。
操作系统会自动维护它，常见操作包括：

添加：收到 ARP Reply 或免费 ARP 时，更新表项。

查询：发送 IP 包前，先查表，有则直接用 MAC；没有则发 ARP Request。

老化：每个表项有生存时间（TTL），超时后删除，重新解析。

删除：收到冲突的 ARP 信息或手动清除。

本项目中的情况：
FPGA 作为 被动响应方，只回复 ARP 请求，不主动发起 ARP 请求，因此 没有维护 ARP 缓存表。
PC 端（如 Windows/Linux）会自动维护 ARP 缓存，记录 FPGA 的 IP↔MAC 映射。

所以在本项目中，ARP 表的操作完全由 PC 完成，FPGA 只管应答，简化了设计。

四、以太网帧结构 + ARP/ICMP 封装图示

1. 以太网帧通用格式
   text
   +----------------+----------------+----------+---------------------+--------+
   |   目的MAC (6)  |   源MAC (6)    | 类型 (2) |      数据 (46~1500) | FCS(4) |
   +----------------+----------------+----------+---------------------+--------+
   目的 MAC：接收方物理地址

源 MAC：发送方物理地址

类型：标识上层协议，如 0x0800=IP，0x0806=ARP

数据：上层协议的数据单元

FCS：帧校验序列，用于 CRC 错误检测

2. ARP 报文封装在以太网帧中
   ARP 直接封装在以太网帧中，类型字段为 0x0806。

text
+----------------+----------------+--------+--------------------------------+--------+
| 目的MAC (6)    | 源MAC (6)      | 0x0806 |       ARP 报文 (28字节)        | FCS(4) |
+----------------+----------------+--------+--------------------------------+--------+
ARP 报文内部结构（28 字节）：

text
+-----------+-----------+----------+----------+----------+
| 硬件类型  | 协议类型  | 硬件长度 | 协议长度 | 操作码   |
| (2)       | (2)       | (1)      | (1)      | (2)      |
+-----------+-----------+----------+----------+----------+
| 发送方MAC | 发送方IP  | 目标MAC  | 目标IP   |
| (6)       | (4)       | (6)      | (4)      |
+-----------+-----------+----------+----------+
本项目中：

硬件类型 = 0x0001（以太网）

协议类型 = 0x0800（IPv4）

硬件长度 = 6（MAC 地址 6 字节）

协议长度 = 4（IP 地址 4 字节）

操作码 = 0x0001（请求）或 0x0002（应答）

发送方/目标 MAC 和 IP 按大端序排列

3. ICMP 报文封装在 IP 包中，再封装在以太网帧中
   ICMP（Ping）不是直接封装在以太网帧，而是先封装在 IP 数据报里，IP 再封装在以太网帧中。

text
+----------------+----------------+--------+---------------------------------------------+--------+
| 目的MAC (6)    | 源MAC (6)      | 0x0800 | IP头(20) | ICMP头(8) | ICMP数据(可变) | FCS(4) |
+----------------+----------------+--------+----------+-----------+----------------+--------+
以太类型 = 0x0800（IP）

IP 头中 协议号 = 1 标识上层是 ICMP

ICMP 头：

类型（1 字节）：0x08=Echo Request，0x00=Echo Reply

代码（1 字节）：固定为 0

校验和（2 字节）

标识符（2 字节）

序列号（2 字节）

ICMP Echo 请求/应答的数据部分通常包含时间戳和填充数据，用于计算往返时延和满足最小帧长。

五、ARP 报文逐字节详解（42 字节，请求 vs 应答对比）

理解 ARP 的核心就是搞清楚：同一份报文，请求和应答到底哪些字段变、哪些不变。下表是完整 42 字节的逐字节对照：

| 偏移 | 字段 | 字节 | 请求（Request）值 | 应答（Reply）值 | 变？ |
| --- | --- | --- | --- | --- | --- |
| 0~5 | 目的 MAC | 6 | `FF:FF:FF:FF:FF:FF`（广播） | 请求方 MAC | ✅ |
| 6~11 | 源 MAC | 6 | 请求方 MAC | 本机 MAC | ✅ |
| 12~13 | 以太类型 | 2 | `0x0806` | `0x0806` | ❌ |
| 14~15 | 硬件类型 | 2 | `0x0001`（以太网） | `0x0001` | ❌ |
| 16~17 | 协议类型 | 2 | `0x0800`（IPv4） | `0x0800` | ❌ |
| 18 | HLEN | 1 | `6`（MAC 6 字节） | `6` | ❌ |
| 19 | PLEN | 1 | `4`（IP 4 字节） | `4` | ❌ |
| 20~21 | 操作码 | 2 | `0x0001`（Request） | `0x0002`（Reply） | ✅ |
| 22~27 | 发送方 MAC | 6 | 请求方 MAC | 本机 MAC | ✅ |
| 28~31 | 发送方 IP | 4 | 请求方 IP | 本机 IP | ✅ |
| 32~37 | 目标 MAC | 6 | 全 0（还不知道） | 请求方 MAC | ✅ |
| 38~41 | 目标 IP | 4 | 被查询的 IP | 请求方 IP | ✅ |
| 42~63 | 补零 | 22 | `0` | `0` | — |

六、ARP「镜像翻转」规律

从上面的表能总结出一条规律：ARP 请求→应答，本质就是**「发送方 ↔ 目标方」互换，操作码 request→reply，其余不动**。

- 请求里「谁问的」（sender MAC/IP），应答里变成「答给谁」（target MAC/IP）
- 请求里「问谁」（target IP），应答里变成「我是谁」（sender IP）
- 目标 MAC 请求时全 0（因为还不知道对方 MAC），应答时填上请求方的 MAC

一句话：**把请求帧里的发送方和目标方对调，就是应答帧**。

七、字节序（大端）

ARP 里的多字节字段——硬件类型、协议类型、操作码、IP 地址——都是**网络字节序（大端）**。所以操作码 `0x0001` 在网线上是两个字节 `00 01`，不是 `01 00`。

本项目 `arp.c` 读操作码就是按大端拼的：

```c
arp_type = (uint16)LCPU_RD_DATA8() << 8;   // 读 RX[20] 高位
arp_type |= LCPU_RD_DATA8();               // 读 RX[21] 低位
```

八、帧长与最小帧长

- ARP 帧 = 14 字节以太头 + 28 字节 ARP 负载 = **42 字节**
- 以太网有**最小帧长 64 字节**（不含 FCS）的限制：小于 64 字节的帧会被接收方当成"冲突碎片/残帧"直接丢弃
- 所以 42 字节的 ARP 帧要**补 22 个 0** 凑到 64 才能发出去

九、ARP 家族的其他类型

| 类型 | 操作码 | 说明 |
| --- | --- | --- |
| ARP Request | `0x0001` | 广播问「谁的 IP 是 X」 |
| ARP Reply | `0x0002` | 单播答「我是 X」 |
| RARP Request | `0x0003` | 反向：问「我的 IP 是什么」（无盘工作站用） |
| RARP Reply | `0x0004` | 答「你的 IP 是 X」 |
| 免费 ARP（Gratuitous） | `0x0002` | 主动广播自己的 IP↔MAC，用于**检测 IP 冲突**或**通告新 MAC** |

本项目只用 ARP Request/Reply，FPGA 作为**被动应答方**，从不主动发 ARP，所以 RARP/免费 ARP 都没实现。

十、本项目 arp_reply() 的实现（c/arp.c）

实现分两步：**三重校验（三道安检）** + **九段构造（边读边写）**。

**三重校验**——三道全过才应答，任一不过直接 `return` 丢弃：

1. 目的 MAC（RX[0..5]）== 本机 MAC **或** 广播（`FF:FF:FF:FF:FF:FF`）
2. 目标 IP（RX[38..41]）== 本机 IP（`Local_IP_ADDR`）
3. 操作码（RX[20..21]）== ARP Request（`0x0001`）

**九段构造**——从 RX FIFO 边读边写 TX FIFO：

| 段 | 写什么 | 来源 |
| --- | --- | --- |
| 1 | 目的 MAC | ← 请求方 MAC（RX[6..11]） |
| 2 | 源 MAC | ← 本机 MAC（硬编码） |
| 3 | 以太类型 | ← RX[12..13]（抄，不变） |
| 4 | 硬件类型+协议类型+HLEN+PLEN | ← RX[14..19]（抄，不变） |
| 5 | 操作码 | ← `0x0002`（硬编码 Reply） |
| 6 | 发送方 MAC | ← 本机 MAC |
| 7 | 发送方 IP | ← 本机 IP |
| 8 | 目标 MAC | ← 请求方 MAC（RX[22..27]） |
| 9 | 目标 IP | ← 请求方 IP（RX[28..31]） |

最后补零 TX[42..63] → `LCPU_WR_PUSH_PACKET(64)` 推出去。

**两个设计巧点**：

1. **不变字段从 RX 原样抄，不硬编码**：硬件类型/协议类型/HLEN/PLEN/以太类型这些请求应答一模一样的字段，直接从 RX 拷到 TX（段 3、段 4）。好处是抄的永远和请求方一致，还省代码。
2. **不用结构体、用偏移量**：`arp.h` 里明明定义了完美的 `arp_frame_t` 结构体，但代码一个都没用——因为 RX/TX FIFO 是寄存器寻址的字节流，没有内存地址给你 struct 指针访问。结构体是"说明书"，真正解析靠 `OFF_ARP_*` 偏移量"按图索骥"。

十一、ARP 怎么验证

1. **ping 触发 ARP**：PC 执行 `ping 169.254.1.1`，如果 ARP 缓存里没有这个 IP，PC 会**先广播 ARP 请求**，收到 FPGA 的应答、建立 IP↔MAC 映射后，**才发 ICMP Echo**。所以"ping 通"背后其实藏了一次 ARP 解析。
2. **抓包看过程**：`sudo tcpdump -i eno1 -n arp`（或 Wireshark 过滤 `arp`），能看到两条：一条 ARP Request（目的 MAC 是广播 `ff:ff:ff:ff:ff:ff`），一条 ARP Reply（单播回请求方）。
3. **看 ARP 缓存**：`ip neigh show` 或 `arp -a`，能查到 `169.254.1.1` 对应的 MAC 地址，这就是 FPGA 的物理地址。
4. **清缓存重测**：`sudo ip neigh flush all` 清掉缓存后再 ping，又能重新看到完整的 ARP 请求→应答过程。
